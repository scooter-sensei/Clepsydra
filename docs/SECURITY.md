# Threat model

Who attacks the filter: the client of a rate limiter, abuse check or dedup that the filter backs. They choose keys (IPs they control, accounts and cards they test, request ids) and when to send. They see the caller's decisions (allowed or blocked) and how long each one took. They don't see memory or the hash key. Running at volume costs them something: requests, accounts or IPs.

What they want, in order of how much it hurts the caller:

1. **Undercount themselves.** Read below a limit while going over it, or read as new while repeating.
2. **Frame someone else.** Push another key's count up, or make it read as already seen.
3. **Slow everyone down.** Pile work onto one lock or one region of the table.

Tags like [A1] point to `go/verify/claims.md`.

Keyed hashing (1–3, 7) holds only if the key stays secret. The default seed is per filter and never leaves the process. `Config.Key` is a 128-bit SipHash-2-4 key: a PRF, the same in every process that uses it, so it can be shared and rotated. The `*At` methods take a hash from the caller and can't check it; pass them only `Hash`/`HashUint64` values of the same filter.

## Using the trust flags

`Touch`, `TouchAt`, `Count` and `CountAt` return a `Result`. A fail-closed rate limit:

```go
r := f.Touch(key, window)
deny := r.Count >= limit ||
	r.Saturated ||               // Count is only a floor
	strict && r.Upper >= limit   // the edge bucket, or a dropped history in the overflow table, could hold the rest
```

`Degraded` means the key likely has a history the stash dropped: its count partly comes from the overflow table and, about 0.3% of the time while that table is full, from another key whose fingerprint matches. For dedup, treat `r.Seen || (strict && r.Degraded)` as a duplicate. Histories under `SpillMin` (4) events are shed when the stash drops them, so a key seen 1–3 times can read new again after a flood; `SpillMin: 1` keeps them too (dedup then survives floods until the overflow table itself overflows, and inserts into a full table cost ~30% more, S35). With the overflow off (`Overflow < 0`), `Degraded` keeps its old, table-wide meaning: some history was lost within a horizon and this key isn't held; strict callers then add `strict && r.Degraded && !r.Seen` to `deny`. A key whose history was lost and that has come back is held again, so it reads low without `Degraded` until the lost events leave the window: with the overflow off, `Upper` is a bound only while `Lost()` hasn't moved within a horizon (found by the fuzzer, A18).

## What is left

- **Volume past the overflow table.** A flood can no longer erase a history, and up to 4x the table's slots in heavy keys it costs other keys almost nothing: the ghost table (`Config.Overflow`, default 5 units per 9 slots, 8.9 B per slot once allocated) holds 3.2 histories per slot, in the less loaded of two buckets. Past about 4.5x its buckets overflow, their floors rise to the flood's weight, and `Upper` covers the keys sharing them: at a 6x flood of 21-event keys a strict limit of 20 turns away 96% of new keys, at 8x 99%, and the offenders' `Count` is gone (their entries were the lightest, so they left first; `Upper` still covers them). Three floors per bucket narrow the damage only while overflow is partial (one bucket per history at slots/2, 4x: 56% → 29%). `Overflow` moves the point; `Floored()` is the alarm (it stays 0 below capacity).
- **Hot entries run out.** A key over 31 events in one unit is promoted to an exact hot entry (one per 128 slots by default). If every entry is in use, a key saturates as before and reads `Saturated` until that unit leaves the register, so a strict caller can enforce only 31 events per unit for it: 31 × 24 / Horizon events/s (12.4/s at a 60 s horizon). `HotRefused` is the alarm; `Config.Hot` sizes the table. Entries are reclaimed once their newest event is past the horizon.
- **Fingerprint matches.** While the overflow table is full, about 0.3% of keys that never spilled match some entry's 14-bit fingerprint in one of their two buckets and read that entry's count, flagged `Degraded`. The count-min sketch it replaced flagged 0% (it hid matches under its noise threshold, and with them most real dropped histories).
- **Repeatedly floored keys.** A full overflow bucket keeps the largest history that left to each floor, which `Upper` adds. A key that leaves a history there, returns, and is pushed out to the same floor again can read low by all but its largest floored history, unflagged. It takes a flood past the overflow table, timed around the key's own returns. Summing floors instead removes it, but a 16x flood of light keys then turns away 100% of new keys under a strict limit (0.1% now), so it was declined (2026-10-09). The stress soak (`go/test.sh stress`) checks that every low answer has a live floor in its bucket.
- **Shed light histories.** A key with fewer than `SpillMin` (4) events in the horizon loses them if it is evicted and the stash drops it (`Shed()` counts these). Getting there still takes about a table's worth of heavier keys per eviction. `SpillMin: 1` keeps everything at ~30% more cost per insert into a full table (A10, S35).
- **Timing.** Off by default: a hit reads one line, a miss two (plus the stash and overflow table while they hold anything), and a first touch inserts, with a cuckoo move for 44% of new keys at 85% load (S38). `ConstantTime` closes most of it at a price: every call spins at least its pad (1 µs suffices for `Touch` on the 2026-10-21 host, where a DRAM access costs ~150–200 ns). A pad that ended at a fixed time leaked through the phase of the spin's clock reads (~37 ns apart here): `Count` at a fixed 1 µs pad gave D 0.019–0.041, visible only at ~10 ns timing resolution; every pad now ends at a random point over 128 ns (64 ns per call on average), which brings it to 0.007–0.014 [S41]. What still shows: calls that run past their pad. Under sustained insert pressure (more than one waiting key per 16 stash entries) every call places one stash set past its pad, for every key alike: that tells an observer the table is under insert load, not which keys were seen. A waiting key whose stash set is full is inserted at once, which takes longer; that happens only while placement falls behind.
- **Restarts** forget everything, and a new random seed changes every hash. `Config.Key` keeps hashes stable, but no state is persisted yet.
