# Reproducing the results

Every claim in these documents is listed in [the claims register](claims.md) with the command that checks it. This page describes the tools behind those commands. All paths are relative to `go/`.

## Requirements

- Go 1.24.7 (the version `verify/expected/` was produced with), bash, git with the full history (the replays build old commits).
- For the model checks: Java 11 or later and `tla2tools.jar` (TLA+ tools 1.7.4).
- For the speed tools: Linux (`cycles/op` needs `perf_event_open`); the DRAM benchmarks need about 2 GB of RAM.
- For the head-to-head's industry arms: Rust (stable; the readings used 1.99.1) with a C linker, network access once to fetch the crates `bench/h2h/Cargo.lock` pins, and about 2 GB of RAM (the exact map holds ~1 GB after the 16x flood).

## Everything at once

```
verify/run.sh           # deterministic checks: they must match verify/expected/ byte for byte
verify/run.sh --speed   # also the speed suite (host-dependent: reported, not checked)
verify/isolated.sh      # verify/run.sh on a fresh copy of the committed history, offline
```

`verify/run.sh` runs vet, the tests, the race detector (`-short`), the suite in ConstantTime mode, in Background mode (`TF_BG=1`) and with realign's hold (`TF_NOCAS2=1`), the accuracy scorecard (`go run ./cmd/tfbench -exact`), the placement limits, the register experiment, the velocity bound, the attacks, the sustained rates, the sketch experiments, the flood sizing and the head-to-head's part 2 (each compared with its file in `verify/expected/`), the bug replays, 300 runs of each racy regression test, the scorecard-history replay, the harness replay and the reverted experiments. `--speed` adds the scorecard's speed columns (three runs), the timing leak (`TF_TIMING=1 TestTimingLeak`) and the ConstantTime pads (`TF_CTEXP=1 TestCTPads|TestCTParallel`). Results go to `$OUT` (default `./verify-report`): `summary.txt` plus one log per check.

Deterministic results depend only on the code and the Go version: the workloads are seeded and single-threaded, and the integer-key hash the harness uses is unkeyed. Expected files were produced on linux/amd64 with Go 1.24.7; other architectures may differ (Go may fuse floating-point multiply-adds there). linux/arm64 under qemu-user matched them (§Other architectures).

**Isolation.** `verify/isolated.sh` runs `verify/run.sh` on a fresh clone of the repository's committed history (a git bundle), with no network, empty Go caches and nothing from the machine's Go setup. Only committed work is verified. With Docker it uses the official Go image pinned by digest (`golang:1.24.7-bookworm@sha256:b8bae5bd9ba9b1f89b635c91c24cc75cea335a16fb5076310f38566fc674b1ec`, from Docker Hub or `mirror.gcr.io`, pulled once beforehand) with `--network none` and the bundle mounted read-only; without Docker (`ISOLATION=unshare`) it needs Go 1.24.7 on `PATH` and unprivileged user namespaces, and runs under a new network namespace (loopback only), `env -i` and fresh `HOME`, `GOCACHE`, `GOPATH` and `GOMODCACHE`. Both set `GOFLAGS=-mod=readonly GOPROXY=off GOSUMDB=off GOTOOLCHAIN=local GOTELEMETRY=off`. The report lands in `./verify-report-isolated`. The last full runs of both paths are in [isolated-runs.md](isolated-runs.md).

## The test tiers

`./test.sh <tier>` with `smoke`, `sanity`, `regression` (`--full` for the replays), `perf [A]` or `stress` (and `all`): [specification/conformance.md](../specification/conformance.md#test-tiers) defines them. Environment knobs: `TF_STRESS`, `TF_STRESS_RACE`, `TF_FUZZ`, `TF_CFUZZ`, `STRESS_RUNS`, `PERF_MAX`, `PERF_ROUNDS`, `PERF_BENCH`, `OUT`.

## The head-to-head

[head-to-head.md](head-to-head.md) is the protocol. Part 1 (Clepsydra, `pingora-limits` and an exact sliding-window log in DashMap under 1x–16x floods) runs on one host:

```
verify/h2h.sh [workdir]     # N=262144 ROUNDS=5 THREADS=12 by default; 56 minutes on the Ryzen host
```

It builds `go/cmd/h2h` and `bench/h2h` (Rust), writes six traces once (`h2h gen`), sizes the count-min estimator to Clepsydra's peak bytes, runs five passes per arm, trace and round with the arms' order rotating, then the 8x and 64x sizing runs, and ends with `h2h report` (validity, then the tables of paper §7.5). Its accuracy figures vary a little run to run (every arm draws its hash seeds per process); its speed figures are the host's. Part 2 (Clepsydra and the ECM-sketch at equal memory) is deterministic: `go run ./cmd/h2h ecm` (~3.5 minutes on 12 threads), checked against `verify/expected/h2h-ecm.txt` by `verify/run.sh` and `./test.sh regression --full`; `go run ./cmd/h2h velcheck` first shows that its workload is the scorecard's (D5's figures). The ECM-sketch's own checks: `go test ./internal/ecm`.

## Replays

`verify/replay.sh` replays recorded results against the commits that produced them; each subcommand prints one result line per case and exits non-zero if a case did not reproduce.

- **`fixes [N]`**: each bug-fix test fails on the commit with the bug and passes on the fix (15 cases: duplicate slots, twice; lost counts under relocation; abandoned moves; the same-tag hand-over; negative ticks; the empty-batch panic; the torn lookup; the ghost epoch race; the ghost add ahead of the clock; the restore behind the clock; the visible move copy; the reclaimed hot entry, twice; the tick range, `tick-past-range`). It copies the current test file into both commits; `verify/testdata/` holds two older versions where the current one calls code the old commits lack (`ghost_test.go` as of 00a9375, `restore_test.go` as of f44e7dd). Racy cases get enough runs that the bug is missed with probability < 1e-4. Fixes proven by deterministic tests on hooks their own commits added (the split history, the eviction racing a move's start, the wait-room transfer, the register epoch, the copy of an evicted key, the wait-room ways, the decay sweep's hold, an insert's hold over an expired occupant, the tag-stripe series, a hot history's exits from the stash) can't run on the code before, so their hook tests are their evidence [R2].
- **`stress [N]`**: the four racy regression tests at the working tree, N runs each (default 300), 4 at a time (`TestAbandonedMoveKeepsCounts` alone, since it needs its eight workers truly parallel). Each test runs in its own directory, and a failing run's summary lines are printed [D14].
- **`history`**: each [scorecard-history](../record/scorecard-history.md) row: re-run that commit's own `tfbench -quick` and compare the deterministic columns with the recorded row [R1].
- **`harness`**: today's accuracy harness (`tfbench -exact`) on every commit that changed the library (every non-test `.go` file of the module's top directory and of `internal/cpu` and `internal/siphash`; only `internal/workload`, the harness's input, is replaced by today's), plus the one older-harness case the [record of changes](../record/changes.md) cites (item 1), compared with `verify/expected/harness.txt` [R3, X31].

What the replays showed when they were extended:

- All fix cases reproduce (fail with the bug, pass with the fix). The duplicate-slot cases had failed to build because `dup_test.go` used a field older commits lack; it now uses `Waiting()` when present. Since a9eb39e the failing-round diagnostic of `abandon_test.go` called `whereIs`, defined in `soak_test.go`, which the commits of two old fixes lack: both entries read build-failed and `./test.sh regression --full` failed, until the diagnostic called it through a variable `soak_test.go` sets, so the file builds alone; then all 15 entries reproduced (16/20 and 17/200 failing before their fixes, 0 after), with the tick range (4f33a45 3/3 → b866d7f 0/3).
- The harness replay reproduced the 34 recorded blocks byte for byte; the library commits since f14d3ea added new blocks (3b5a427 and 6c051d0, then the later ones). It had watched only `filter.go` and `register.go`, so it skipped commits that changed only `ghost.go` or `hot.go` (42cc598, 00a9375, 3a44c40); it now watches every library file, those three blocks are byte-identical to the blocks before them, as the commits said, and two full replays agree byte for byte [X31]. At 8cd2f4e it reproduced the 47 recorded blocks plus five new ones (17f14d9 included). The nine library commits ccf23af through 0779e1e, and the three of the tag-stripe series, each added a block equal to `exact.txt`: none of the concurrency fixes changes a single-threaded result. - `./test.sh regression --full` passed in a clone with full history at a82f5c2.

## Reverted experiments

`verify/experiments.sh` re-runs the deterministic effect of each reverted experiment: each patch in `verify/experiments/` is applied to a fresh export of fbe6968 (the last commit of the improvement loop; its library code matches HEAD's apart from comments), then today's accuracy harness and the patch's own tests run on it, compared with `verify/expected/experiments.txt`. Speed effects are host-dependent: `verify/ab.sh fbe6968 fbe6968+verify/experiments/<name>.patch <bench>`. [experiments.md](experiments.md) describes each patch.

## Model checks

`verify/tla.sh [model...]` model-checks the slot protocol's concurrent parts with TLC (TLA+ tools 1.7.4, from github.com/tlaplus/tlaplus/releases, at `$TLA2TOOLS` or `~/tools/tla/tla2tools.jar`; Java 11 or later). Models: WaitRoom, RegisterEpoch, Relocate, RoomWays, SlotHold, TagStripe, BumpABA, HotEntry (default: all), in `verify/tla/`; [the paper](../paper/05-concurrency.md#56-model-checks) says what each checks. Each run translates the PlusCal (`pcal.trans`) in a scratch directory, so the committed `.tla` stays as written, and prints one line per run; the script exits non-zero if a run's outcome isn't the one wanted. Each model runs the protocol as committed, exhaustively at small sizes, and then each of its guards undone, which must break an invariant; `RegisterEpoch` runs realign both ways as committed, its hold and its 16-byte CAS on amd64 (A33), and `BumpABA` and `RegisterEpoch` also run experiment E21's 16-byte count, which must hold. `TLA_BIG=1` adds the large sizes the claims cite (WaitRoom 2 touchers × 2 rounds, 72 M states; RegisterEpoch 3 touchers, 52 M states: tens of minutes each); `TLC_WORKERS` (default 4) sets TLC's threads. The models are not in a test tier: they change only with the protocol, and some sizes take tens of minutes. `verify/tla/experiments/HotCells.tla` models experiment E23 and is not in the default list.

## The concurrent fuzzer

The soak and `TestFuzzUpper` give each key one goroutine, so a key is never read while another goroutine touches it. `TestFuzzConcurrent` (`TF_CFUZZ=<duration>`, e.g. `10m`) runs the fuzzer's configurations with 2 to 2×GOMAXPROCS goroutines on one filter, a fifth of its cases in ConstantTime and a fifth with Background (the placer a goroutine). Each goroutine owns its keys and checks `Upper` on every Touch and Count, as `TestFuzzUpper` does. One operation in eight is on a few keys every goroutine shares, and a Count of a shared key must cover the touches that returned before it began. The clock is shared, and callers read it with a lag of up to two units; with `TF_CFUZZ_STRAGGLE=1` one goroutine of every case is a straggler, its calls half a horizon to a horizon behind (a caller descheduled that long, or one passing its own timestamps). The straggler found nothing in 10 minutes at 0779e1e, but it has no practical power over the slot holds of claims A26 and A27, which need its touch within a few nanoseconds of a hold; their hook tests are their evidence.

Some races need two keys of the same 12-bit tag to meet in one slot, since their first registers in one unit are bit-identical (A28, A29): with real tags one hand-over in 4,096, and the fuzzer found those kinds once per 30 to 60 minutes. `TF_CFUZZ_TAGS=n` gives every key a tag from n values and a fingerprint unique in the case (capacity at most 4,096, so fewer than 65,536 keys), so two keys share a tag one time in n: at n = 8 those races come 512 times as often. `TF_STRESS_TAGS=n` does the same in the soak. A case's configuration and streams come from its seed (`TF_CFUZZ_SEED`, default 1), but its run depends on its races, so a failure doesn't replay exactly: `TF_CFUZZ_CASE=<seed>` runs that case `TF_CFUZZ_RUNS` times (default 20). A trace build (`verify/experiments/trace-concurrent.patch`, build tag `tftrace`) dumps the records naming a failing case's key.

## The power of the checks

A check that can't fail proves nothing, so each was run against bugs it should catch.

- **The fuzzer's second direction** [A36]: 2.35e8 operations (186 cases) with both directions checked found no violation either way. A restored history counting its touch twice failed in 3 of the first 136 cases (`TF_FUZZ=3e7`), `Seen` a unit past the window in 3 of the first 211; each within the first 13,000 operations of its case. Both pass the `Upper` check alone. `TestFuzzUpper` with the ghost-clock fix of 00a9375 undone fails 6 of 310 cases in 3.3e8 operations [A18].
- **The soak's hot entries per worker.** The soak checks `Upper` only where an answer isn't Saturated, and about 70% were. By source (30 s soaks), nearly all were refused promotions (a register past its 31 events in a unit with every hot entry in use: the soak had 10 per worker) while the pool was 1–2x the table; with the pool at 4–8x, a quarter of answers are histories in the overflow table, Saturated by design. Hot entries per worker against the share Saturated: 10, 62.6% (plain), 63.0% (Background), 67.4% (Background, tags shared 8 ways); 20, 56.9%; 40, 46.0%; 80, 24.2%; 160, 8.7% (Background with tags: 0.9%). Operations in 30 s stayed within 10% (100.2 M at 10, 90.9 M at 80, 111.9 M at 160). By the rule (the smallest count under half of the share then), the soak has 80 per worker (39b24a5), where it checks ~70% of answers: twice the answers checked, and 60 times the promotions (3,466 to 214,474), so hot entries' own races get exercised. In the plain runs at 9be2f39, 19–64% of checked answers had been `Saturated`, probably because the soak's 192 heavy keys (8 per worker) outnumbered the 37 hot entries of its 4,096-key filter.
- **The soak against each fix.** On 35d7a30 (before A28–A30) and that tree with two of the three fixes put back (noA, noB, noC: the named one missing), the Background soak with tags shared 8 ways, 60 s, 10 hot entries per worker: 35d7a30 failed 2 of 3 runs, noB 1 of 5, noA and noC 0 of 5; both first low answers were one under the true count (3 for 4, 6 for 7). So the soak found A29's bug alone once in five runs, and A28's and A30's alone in none; neither did 5-minute fuzzer arms with tags (noA and noC 0 failing cases; 35d7a30 10, noB 7). At 80 per worker (six runs per arm, alternated): 35d7a30 failed 4 of 6 at 10 per worker and 5 of 6 at 80 (2–11 unflagged answers per failing run, each first one `Degraded` and below the true count); noB 0 of 6 at both. The first rule had counted answers checked, not bugs found, and at 80 per worker heavy keys move to hot entries, off the register paths A28–A30 fixed; by the second rule (80 keeps the default if its failures are at least those at 10 less two), the soak keeps 80 (39b24a5). A29's bug alone is beyond the soak at either count (1 failure in 17 runs); the concurrent fuzzer with tags finds it (7 failing cases in 5 minutes).
- **The stress tier's concurrent fuzzer** (one run per arm, seed 1): the 5-minute fuzzer plain 0 failing on every arm (35d7a30, the series with A28, A29 or A30 undone, the series); with tags shared 8 ways 35d7a30 10 failing of 1,106 cases, A29 undone 7 of 993, A28 undone 0, A30 undone 0 (A30's race doesn't need a shared tag), the series 0; the 60 s soak with tags shared 8 ways low at 35d7a30 (a spilled history 19 of 20: A29's signature), 0 with any one fix undone, 0 at the series. So it catches A29 within minutes; A28 (about one failure per 10–15 amplified minutes) and A30 rest on their hook tests [A22].
- **Wider amplified arms** (at the A33 tree, the soak at 10 per worker): the concurrent fuzzer with the straggler and tags shared 8 ways, 0 of 1,935 cases (10 min, seed 7000); tags shared 4 ways, 0 of 1,901 (seed 8000). Soaks with tags shared 8 ways, 60 s, three each: ConstantTime 0 unflagged in 30.0–30.3 M answers checked (8.6–9.0% Saturated: at a third of the plain soak's rate, fewer keys pass their registers), plain 0 in 66.6–67.1 M (67.5–67.6% Saturated). At d0ac628, the soak at 80 per worker, 60 s: 0 unflagged plain (60.6 M answers checked, 29.8% Saturated, 405,677 promotions) and Background with tags shared 8 ways (50.5 M, 28.5%, 396,115).
- **Mutations of Background** [A19]: with the commit's move check removed, `TestBackgroundConcurrentCounts` fails 3 of 3 runs within 6–16 rounds; with a touch leaving an expired room entry in place, fuzz case 54 fails.

## Other architectures

- **32-bit x86** needs no emulator: an amd64 Linux kernel runs 386 binaries, so `GOARCH=386 ./test.sh sanity` runs the suite as 32-bit code. The 386 build has no 16-byte CAS, so realign holds the slot as on arm64. It passes plain, `TF_CT=1` and `TF_BG=1`: the first time the library ran on a 32-bit platform. (`New` had clamped `Hot` to `hotIdxMask`, 2^43−1, an untyped constant that overflows a 32-bit `int`, and five tests and `tfbench` used `1<<40 + i` as an `int`; fixed in 04fc643.)
- **arm64** without its hardware: Go's static test binaries run under qemu's user mode, so `GOARCH=arm64 GOFLAGS=-exec=qemu-aarch64 ./test.sh <tier>` runs the tier as arm64 code on an amd64 host (until then the claims held for linux/amd64 only). That tests the arm64 build and its own paths (realign's hold, `internal/cpu/prefetch_arm64.s`, and whether Go's fused multiply-adds on arm64 change any deterministic result), not arm64's memory ordering: qemu runs the guest's atomics on the host's. With qemu-user 10.2.1 at a6f7ea6:
  - `./test.sh regression`: every expected file matches byte for byte.
  - `./test.sh sanity`: everything passes but `TestCTPadEndIsDithered` (padded calls must end spread over more than one clock read), which read a spread of 21–60 ns against 80. Under qemu a clock read costs 566 ns (smallest step 340 ns; natively 48.5 ns and 30 ns), so the pad's 128 ns dither is under one read and the end follows the read's phase. The test is right: on such a clock the dither does nothing. In the checks of a88887b–b866d7f (verification log, below), arm64 under qemu-user passed `./test.sh sanity` (unit 99 s, ConstantTime 164 s).
  - 60 s soaks, plain and Background: 0 unflagged in 9.1 M answers each. Only 0.01% of them were Saturated (1,132), against ~70% natively: emulated, the keys' rates stay under their registers' capacity. The concurrent fuzzer, 10 min at seed 10000: 0 of 441 cases. `TestFuzzUpper`, 2e8 operations: passes.
- `go vet` passes for linux/amd64, 386, arm64, darwin/arm64 and windows/amd64 (at c0e32d1; the `cycles/op` helper is Linux-only, a stub elsewhere).
