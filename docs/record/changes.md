# Changes

Every adopted change to the filter, in the order it landed, with its measured effect. The numbers are stable: the claims register cites them ("changes 10", "changes item 16"). [The claims register](../artifact/claims.md) maps each number here to a check (deterministic, replayed from git, or host speed) and marks the ones that turned out wrong; the corrections are given inline. Speed figures up to item 26 are from the Xeon host and from item 27 on from the Ryzen host ([hosts](../README.md#hosts)). Bugs are also listed, with how each was found, in [defects.md](defects.md); ideas that were tried and not adopted are in [decisions.md](decisions.md). The scorecard row of each change is in [scorecard-history.md](scorecard-history.md) (`./bench.sh "label"` in `go/`: race tests plus `cmd/tfbench`, appended there).

## Placement, layout and the register

1. Partial-key cuckoo relocation (alt line from fp), iterative deepening to depth 2. Missed keys at 2.5x load: 5.0% → 0%.
2. Adaptive relocation budget (failure EWMA). Overfull-table insert: 12µs → ~0.4µs as first recorded; re-measured 3.7 µs → 0.30 µs (claims S5).
3. 28-bit slot identity (4-bit epoch, 12-bit tag). Static FPR 2e-7 → 4e-8 as first recorded (1 and 2 events in 5M/50M probes); at 1e9 probes it is 1.96e-7 → 1.40e-8 (claims X7).
4. CheckAndTouchBatch (overlapped misses). Cold hit ~100ns → ~45-55ns/key.
5. Any-size table (multiply-shift index, self-inverse alt), default 85% load: 42 → 19 B/key with 0 misses up to 94% load.
6. Relocation depth 3 / budget 500: misses at 98% load 0.19% → 0.066%. Correction (claims X6): measured against 4bde715; the commit just before (6aa1c1b, depth 4 / budget 1000) missed 0.011%, so this change raised misses. Its insert-speed reason was not recorded; measured later, inserts 7–33% faster (S12).
7. Velocity register: 7 age-graded buckets (H/24 near now), closed-form advance, spill on overflow. Velocity MAE 0.129 → 0.087; heavy hitters no longer cap at 255.
8. Register fast paths: lazy victim scoring, in-place same-unit increment, reciprocal instead of divide.
9. VelocityCount estimates from the register's own epoch (no re-bucketing). MAE 0.087 → 0.081. Cache-resident 123 → 45 ns as first recorded; correction (claims X20): 88 → 71 ns re-measured.
10. CoarseClock option (cached clock, one refresher goroutine). String path 172 → 110 ns.
11. Concurrent first touches of one key no longer land in two slots (striped lock on the miss path only). Was ~12% duplicate slots and ~5% lost counts with 8 racing writers (replayed: 13.5% and 8.0% in one run; it varies). Correction (claims X15): the lock left a rare duplicate (10 of 400 runs under CPU load, 1 slot each), which item 16 closed. Steady insert +~15 ns.
12. Same-unit counter increment picks the first non-full bucket with one TrailingZeros instead of a loop. Hot-key hit 44 → 32 ns.
13. Displaced bit (taken from the timestamp, now 47 bits): an entry records which of its two lines it is in, and lookups match it. A key is compared only with entries homed at its own primary line. Static FPR 3.2e-8 → 1.8e-8 (1e9 probes), no speed cost. Storing which bucket choice was used is a known way to extend a fingerprint by a bit.
14. `Ticks` clamps negative durations to 0. A negative window used to wrap to a huge one and report every key as seen.
15. `TouchAndCountBatch` and `VelocityCountBatch` (same overlapped loads as CheckAndTouchBatch). Median of 6 runs, 1M-key table: TouchAndCount 154 → 106 ns/key, VelocityCount 129 → 83 ns/key. Empty batches no longer panic.
16. Installs publish the new key's register together with its word0, and touches only update a register that still carries their tag. A touch landing mid-install or mid-relocation used to reset a hot key's register: 12 of 20 runs of the relocation race test lost counts (up to 70), now 0 of 20 (replayed: 4–8 of 40 before, 0 of 200 after; the test itself was corrected, claims X14). It also closed the residual duplicate-slot race from item 11. Saturated inserts ~10% faster (one write fewer); correction (claims X21): no measurable change when re-measured. Correction (claims X17): two rarer causes of lost counts remained; items 18 and 19 closed them.
17. Scorecard: `hit DRAM` column (32M-key, ~600 MB table). The Xeon host's L3 is 260 MB, so the 1M-key "cold" table (20 MB) was really L3-resident. On DRAM: hit ~207 ns, batched ~95, absent-key ~115, VelocityCount ~190 (`go test -bench Huge`). Hits are latency-bound there because the CAS stops later lookups from overlapping (a hypothesis, not tested); batches recover that overlap.
18. Abandoned moves keep their counts (4a037a5). A move whose source was touched mid-move withdrew its copy with whatever the copy had counted, and a touch still holding the copy could count into the dead slot. The copy is now retired word1 first and its extra events are added back. `TestAbandonedMoveKeepsCounts` (64 hot keys, 8 workers, 99% load): 2% of rounds lost counts before, none after. (The fold was removed again in item 46, once copies were hidden.)
19. Slot hand-over can't misdirect a count (d7fb2b5). A touch that had checked word0's fingerprint could CAS word1 after the slot went to a key with the same 12-bit tag. Installs now set word1 to a reserved busy tag first and touches re-read word0 after word1. Same test with shared tags: about 1 in 1,600 rounds lost a count before (34 of 200 runs), none in 60,000 after. Speed: see [speed-runs.md](../artifact/speed-runs.md).

## Security

20. Keyed integer hash (2d4682b). `HashUint64` is a method keyed like `Hash`: a random seed, or SipHash-2-4 under `Config.Key`. The unkeyed SplitMix64 finalizer could be inverted to forge a victim's identity, evict it with 168 events, or put every first touch on one lock stripe (claims A1–A3). Cost: +3 ns per integer hash with the seed, +15 ns with SipHash (S26).
21. Eviction stash (2d4682b): evicted live keys keep their history in a 4-way stash (1 entry per 64 slots, 0.44 B/key) and get it back on return. Missed keys at 1.15x: 58 → 0 (D1). Speed (S27): saturated inserts +42% (every insert evicts and stashes), hot VelocityCount +12%, other paths within ~10%. A flood that overruns table and stash still erases a history, but the key then reads `Degraded` (A3). The stress test caught a lost-count race in the first version (a stash copy withdrawn after another eviction had replaced it); victims are now stashed under their own claim stripe (A6).
22. Saturated bit and trust flags (2d4682b). One timestamp bit (47 → 46 bits, ~2.2 years at 1 µs) marks a register that overflowed. `Touch`/`Count` return `Result` with `Upper` (edge bucket counted whole), `Saturated`, `Restored`, `Degraded`. Contract: not Saturated ⇒ Upper ≥ exact, 0 exceptions in 261,538 queries (A4, A5). A density heuristic tried first missed 689 of 187,219. Counts unchanged (D5, D7 identical).
23. Overflow sketch, per-key Degraded, ConstantTime. Histories the stash drops go to a count-min sketch over (key, Horizon/4 slice), 16-bit counters, one column per 8 slots (7.1 B/key): a flood no longer erases anything (Lost 0) and `Upper` never reads below the truth (A3, A7). `Count` adds a count-mean-min estimate only above 3σ of the noise, so keys that never spilled keep exact counts, and sets `Degraded` per key (0% of new keys during floods, was 100%). Strict limit of 20: 0.1% of new keys turned away after a 1x-slots flood (was 100%), 100% from 4x. Big floods still hide dropped histories from `Count` (A7). Tried first: restoring sketch counts into the table (the inflated keys then evicted real ones: a never-evicted offender read 992), plain count-min Degraded (99% of new keys flagged at 1x), noise σ from event totals (ignores that histories arrive in lumps; 18% false Degraded at 4x). `ConstantTime` (duration pad): seen-vs-unseen guess from one timing 85–89% → 51% at 3 µs (S28). Speed (S29): saturated inserts +65%, others within ~10%.
24. Security and cost (dd30cbc..08c8ea0 → 150fac4; [paper §6.5–6.6](../paper/06-security.md#65-evidence-floods)). The overflow sketch is now 8-bit × 4 rows × Horizon/2 slices, one column per 4 slots, so a column's ring fits one word (one load per row instead of two; two thirds of the memory buys twice the columns, so it is the same or better than the old shape at every flood size), allocated on the first spill (normal load never drops a history: D1, 0 missed at 1.15x): 4.7 B/key under attack (−34%) and 0 otherwise, was 7.1 B/key always (A9, D6). Histories under 4 events are shed (`SpillMin`, `Shed()`): a 16x flood of one-event keys turns away 0% of new keys under a strict limit (was 100%), and evicted offenders after a 1x heavy flood read Count 18 of 20 (was 0) (A7, A10); in the 1x flood, 102 spills instead of 3,693. Saturated inserts 31% faster (S32). Tried and documented: sleep, adaptive and yield pads for ConstantTime (all worse than spinning, S30), SipHash-1-3 (−35% keyed hash cost, not adopted, S31), 3 rows, wider or 16-bit shapes ([decisions.md](decisions.md#overflow)).
25. Overflow and ConstantTime, under one constraint: no extra cost (memory, insert or lookup time). The overflow count-min sketch is replaced by a ghost table in the same bytes (one 21-bit entry per dropped history, bucket floors keep `Upper` a bound; 4.7 B/key under attack, 0 otherwise): a 2x heavy flood turns away 1.8% of new keys under a strict limit of 20 (sketch 88–90%) and keeps 195 of 200 offenders' Count (sketch 0); reads take one line instead of four (A7, A11). Cost: 0.1–0.2% of new keys read `Degraded` through fingerprint matches while it is full. `ConstantTime`'s Count pads to its own tracked p99.5: 3.4 → 1.05 µs per call at the same leak, 2.1x the throughput under load (S33, S34). `AutoPad` tracks Touch's pad too. Alternate lines are loaded together before the cuckoo search (S35): removing it made near-full and saturated inserts 9–10% slower in a 5-round A/B; an earlier A/B had measured no change, so treat it as small.
26. Test tiers (3b5a427): `test.sh` smoke, sanity, regression, perf and stress; `spec/vectors/` conformance traces every port must reproduce; the concurrent soak `TestStressSoak` checks `Upper` against true counts. Its first finding: a history leaving the stash was spilled after the stash lock was released, so a concurrent Count could miss it (6c051d0, spill under the lock; A13).

## Correctness under concurrency, the count ceiling and floods

27. Torn two-line lookup (6af5480). A relocation that moved a key from its alternate line into its primary between a lookup's two scans hid a live key: Count and Contains answered absent (Upper 0, unflagged), and ConstantTime touches inserted the key a second time. Moves count begun and done per claim stripe; a miss that overlapped a move looks again. `TestReadDuringRelocationFindsKey`: 1–6 bad reads in every run before, 0 in 40 after (R2: 6 of 10 → 0 of 10). ed48f7e folded the check into read()'s one scan: ContainsAbsent 0.89x (S39).
28. Ghost add read its epoch once, outside its retry loop (642c3ef): an add that raced an epoch change decoded a newer entry as four slices old and overwrote a live history, unflagged. Each pass re-reads the epoch and commits only while it is unchanged. `TestGhostEpochRace`: 10 of 10 runs fail before, 0 of 10 after (R2).
29. Hot entries (e9974b9): a key whose register would overflow (31 events per Horizon/24 unit, 12.4/s at 60 s) moves to a 64 B entry of 32-bit counters, one per 128 slots, allocated on the first promotion (0.6 B per key once allocated). Steady 10–5,000 events/s read exact at 5–60 s windows, 0% Saturated (was within 1% only up to 12/s, Saturated from 13/s; A15, D7). Heavy-hitter and random attack queries: 0 Saturated (was 73,606 of 74,319 and 136,124 of 187,219), still 0 unflagged Upper < exact (A4, A5). Velocity MAE 0.0809 → 0.0807.
30. Evictions and moves of one key exclude each other (5524228, a02fe9b). An insert could evict a key's copy or source between a relocation's copy and its hand-over and split the key's history; and an evictor that read the source before the move began could still take it. Moves and evictions now count themselves per stripe with sequentially consistent counters and check each other (a Dekker handshake): one of two that overlap backs off. Deterministic tests on new hooks: 2 and 1 of 3 events before, 3 of 3 after; 1 of 2 before, 2 after. Inserts 1.02–1.03x (S39).
31. Ghost entry spilled by a clock behind the key's last touch (2890196): its slice decoded as four old, so it was skipped and then freed. The epoch now moves to the later of the clock and the history's newest event. `TestGhostAddAheadOfClock`: 3 of 3 fail before, 0 of 3 after. Items 28, 30 and 31 were the soak's unflagged lows (X30): the trace build (`verify/experiments/trace.patch`) showed each one; campaigns of 60 s runs went 15 of 20 clean → 9 of 12 (handshake only) → 20 of 20 (A16, A12).
32. Two-bucket ghost table, three floors, new sizes (a6aa29e). Each dropped history goes to the emptier of two buckets, a bucket has three 7-bit floors picked by fingerprint, Overflow is 5 units per 9 slots and the stash one entry per 16 slots. Strict limit of 20, new keys turned away after a heavy flood: 2x 1.80 → 0.12%, 3x 89.2 → 0.17%, 4x 100 → 0.29%, 6x 100 → 96.3%, at 31.1 B per key (27.1 before; A14). All 200 offenders keep their Count up to 4x (0 at 4x before). `Floored()` counts histories that went to a floor: the alarm for a flood past capacity. Cost: ~0.3% of new keys read Degraded through fingerprint matches once the table is full (two buckets read).
33. Lazy stash and `Bytes()` (0add825, f304277): the stash is allocated on the first eviction, like the overflow table and hot entries, and lazily allocated tables are prefaulted. A filter at design load holds 18.8 B per key (D17); `Bytes()` reports what a filter holds now. Inserts 0.98–1.01x.
34. ConstantTime inserts wait in the stash (b798b1f). 44% of unseen-key inserts at 85% load need a cuckoo move (p99 2.4–3.5 µs; S38), which is why `Touch` needed a 3 µs pad (the security study had named cutting the slow inserts that set the pad's floor as the next lever). In ConstantTime a first touch whose two lines are full waits in the stash, and every call places waiting keys before its own work, as many steps as the pad leaves. Touch at a fixed 1 µs pad: 61.4% → 51.1% / 52.8% correct guesses (two runs); AutoPad settles at ~1.0 µs (was 4.3), 50.6% (S36). Default paths 0.98–1.02x; a ConstantTime call at the 1 µs pad takes 1.5–1.9 µs on average under a 50%-unseen load (forced placement). Deferring evictions and relocations had been declined earlier because a key waiting in the stash would make its next touch take a slow path; in ConstantTime every call reads its stash set anyway, so a waiting key costs its next touch nothing extra.
35. Lock-free same-unit add for hot entries (76b5b9a): bucket 0 of a hot entry is one word (count, closed bit, generation), so a touch in the entry's own unit adds with one CAS instead of the entry lock (the lock and its CAS took ~37% of CPU under Zipf at 6 goroutines; S40). Zipf s=1.1 at 90% load: 28.5 → 33.2 M ops/s at 6 goroutines, 29.9 → 44.1 at 12 (S37).
36. Replay tooling (4b31a89): today's tfbench runs on library versions without `Bytes()`, so `verify/replay.sh harness` covers every version; the fix replays cover the three new replayable bugs (R2).
37. Restore behind the last touch (e9ceb3b): a key taken back from the stash by a caller whose clock was behind its last touch got that older clock as its last touch, so a later Count whose window began between the two read nothing (`Upper` 0, unflagged); in ConstantTime, likewise for a waiting key touched in the stash. The key keeps the later of the two. `TestRestoreBehindLastTouch`: fails before, passes after (R2). The 60 s soaks at 4b31a89 had not hit it.
38. Fuzzer of the `Upper` contract (`TestFuzzUpper`, A18): seeded single-goroutine cases over random configurations, load from idle to 64x capacity per horizon, and lagging clocks, checked against an exact model on every Count and Touch; a failure replays by seed, and `TF_FUZZ_TRACE` follows one key. It found item 37 and the overflow-off gap (X32: with `Overflow < 0` a key that comes back after a lost history reads low without a flag; now documented). 1.004e10 operations, 0 violations (34 min on the Ryzen host); with 2890196's fix undone it fails 6 of 310 cases. `./test.sh stress` runs 1e9.
39. ConstantTime pads end at a random point over 128 ns (5b58d63): a pad ending at a fixed time ended at a phase of the spin's clock reads (~37 ns apart) that followed the call's work; Count at a fixed 1 µs pad leaked D 0.019–0.041, now 0.007–0.014, for 64 ns per call (S41). Touch at 1 µs reads 50.4–50.9% in three runs: target 13 met.
40. Velocity: the newest bucket's last event, at lastTouch, counts whole (395f738): MAE 0.0807 → 0.0779, steady 1 s windows exact at every rate but 12–13/s. `TestVelocityBound` shows what is left is mostly the register's information: under a uniform model no estimator reading it gets below 0.058, and 0.05 needs ~1.25 s resolution near now (D18).
41. The cuckoo search loads one candidate's four next lines together before trying them (S42): 90% load p99 4.4–4.9 → 3.8–3.9 µs, 3-move inserts 12–25% faster; free-slot, 1-move and most 2-move inserts unchanged. Host probes (`hostprobe_test.go`): memory parallelism (S42) and how often the host takes the CPU away (S43).
42. A key that waited for a slot is not Restored (981cd70): in ConstantTime, a waiting key whose next touch installed it read `Restored` and was counted by `Restored()`, though it was never evicted. `TestCTWaitingKeyNotRestored` fails before, passes after.
43. A lost history counts as recent until a horizon after its newest event (c12f98b): with the overflow table off, a dropper whose clock lagged the history's last touch ended the `Degraded` span early, so a returning key could read low without a flag. Found by the fuzzer in a Background case (fuzz case 303). `TestLostAtNewestEvent` fails before, passes after.
44. `Config.Background` (c849b7e, off by default): no first touch searches on the call path. A key whose lines are full waits in a wait room (0.2 B per slot, on the first wait) and a placer goroutine places it, without the key's claim stripe; the commit is a short guarded install. At 85% load inserts over 2 µs 1.3–3.1% → 0.16–0.19%, p99 2.1–2.8 → 1.0–1.1 µs; 90% 9–11% → 0.2–0.3% (S45). Absent-key lookups 1.08–1.12x; nothing else measurably slower (S46). Counts exact under concurrency, with power checks on two mutations (A19). Target 11 on the Ryzen host is bounded by the host: a 0.5 µs busy loop is over 2 µs in 0.05–0.15% of calls.
45. Batches prefetch their chunk's lines and touch each key, in order, from the slot found (22735cd): target 8 met, 9.57 → 11.53 M keys/s at 90% load (S48; other arms E20, `batch-arms.patch`). In ConstantTime the warm pass does the same work whatever the table holds (7f242b1, from the security review).
46. Four fail-open races, each with a deterministic test on a hook and a TLA+ model (`verify/tla.sh`): a touch taking a waiting key out of the wait room counts as a move (15bbc28, A20); a touch 8+ units past a register's unit moves word0 and the register together (5e21d7e, A21); a relocation's copy stays hidden until the hand-off, so a key is never live in two slots, and the fold that repaired abandoned copies is gone (0c08517, A23); a key's wait never takes a wait-room way the placer is committing (277f9ed, A24).
47. The concurrent fuzzer (`TestFuzzConcurrent`, 6534f47, A22): the fuzzer's configurations on 2 to 2xGOMAXPROCS goroutines, own keys and shared keys whose reads race their touches. It found A21, A23 and A24.
48. A hot key's history recalled after its hot entry was reclaimed starts afresh, with the recalling touch counted (5638eac, A25): before, that touch went uncounted and the next reset the register (Upper 1 for 2). Found by the concurrent fuzzer (case 4509) and a trace build; `verify/replay.sh fixes` replays it.
49. The decay sweep takes an expired slot as install does, word1 busy first, its hold counted as a move (A26): before, a first touch of the same key could take the slot between the sweep's two writes with a register bit-identical to the old one, which the sweep then cleared (the key's next touch went into a second slot; an event lost). Found by the concurrent fuzzer (case 1426) and a trace build (7236f76).
50. An insert that takes an expired slot counts its hold as a move of the occupant's stripe (c1cbace, A27): a touch of the occupant two thirds of a horizon behind the inserter, during the hold, put the key in a second slot. Found by reading A26's fix. Every hold of an occupied slot now counts as a move.

Items 51–53 close every open kind of the concurrent fuzzer, all from one family of race: a CAS from a value read earlier succeeding on a slot that changed hands, since a same-tag key's word1 can be bit-identical ([paper §5.2](../paper/05-concurrency.md#52-the-race-family-a-cas-from-a-value-read-earlier)). Amplified by giving keys one of 8 tags (`TF_CFUZZ_TAGS=8`), from one failure per 30–60 minutes to a few a minute.

51. Holds count on the stripe of the tag in the word1 their CAS takes (43e707b, A28): a hold counted on the stripe of the key whose word0 it had read (none over a word0 of 0), but its CAS takes whoever has that word1 then, a key installed between its two loads or a same-tag occupant. That key was hidden with no move counted on its stripe: a second slot, or a read of absent (cases 3974, 1220).
52. A touch's count that landed in a same-tag key is counted again (200e5ea, A29): the count's CAS compares word1 alone, so a same-tag newcomer with a bit-identical register took the event (case 12598, the soak's low). bump reads word0 after its CAS and, if the slot changed hands, waits out any hold and counts afresh only on its own tag (`strayed`). Residuals: ~6.6e-10 of counts high, ~6e-17 low. The first version, counting afresh on any change, read one high in 2–125 of 300 racy-test runs.
53. A stale hot slot resets under realign's hold (9464187, A30): the reset was a CAS from the hot pointer after word0 moved, and a touch between the two added to the entry or demoted it, losing its event (cases 4291, 3490).
54. A hot history that leaves the stash takes its entry with it (0becd6e, A32): a touch of a hot key moves word0, then adds to the key's entry by identity. If the key was evicted in between and its history left the stash, spilled or dropped by a full set as weighing nothing (its entry's events past the horizon, the add not yet in it), the add landed in an entry nothing pointed to (case 9787, both exits). The spill closes the entry and spills its last state, and a full set's lightest way leaves through the spill even with no events in the horizon, so the add fails and the touch counts afresh.
55. Realign by one CMPXCHG16B on amd64 (7a9d87f; E22, A33, S52): a touch 8 or more units past its register's unit moved both words under a hold (word1 busy, counted as a move of its stripe); it now moves them by one 16-byte CAS from the two words read, so no lookup waits and no move counter line is written. Sparse touches from every core 14–15% faster in a program importing the library (one core 1.5–3%). TouchAndCount, which never realigns, reads 1.11 in the test binaries at 7a9d87f: placement, since a size-matched control with no E22 code reads 1.12 (the importer's 1.08–1.10 is only partly explained). Other architectures keep the hold (`TF_NOCAS2=1` tests it on amd64).

Items 56–59 came from a review of every library file and the test suite against the claims, looking for what the checks could not see.

56. A read of the overflow table loads its lines again if an add moved the epoch meanwhile (b2ff9b1, A34): it had decoded them against the new epoch, and an entry the move's sweep cleared after the load read four slices younger, so a history dead for a horizon read live (`Seen`, its whole count, `Degraded`). `TestGhostReadAcrossEpoch` (hook) fails before, passes after. Found by reading `ghost.go`.
57. Ticks stay inside 46 bits (a07e5a0, A35): `MaxTick` (2^46−1) exported; `New` rejects a `Clock` already past it and a horizon of `MaxTick` ticks; an insert, a realigning touch and a sweeping decay step panic past it, before any lock. A caller passing Unix microseconds to the `*At` methods had every key read back unseen with no count (a rate limit failing open); the built-in clock got there after 2.2 years at 1 µs, 19.5 hours at 1 ns. Hits and counts don't check (their placement-randomized speed reading, S54). `TestRegressTickPastRange` fails before, `TestTickRange` covers every entry point.
58. 32-bit builds (550f84a): `hotIdxMask` through `uint64` in `New`, `1<<40` constants in five tests and `tfbench`. 386 runs natively on the amd64 kernel: `go test -short` passes plain, ConstantTime and Background.
59. `TestFuzzUpper` checks the other direction too (A36): what the register answers counts no event from further back than its edge bucket reaches, and `Seen` holds exactly when the key has an event in the window. The `Upper` check passed a double-counted restore and a late `Seen`; the new check fails both within a case's first 13,000 operations.

## Measurement

60. Benchmarks report `cycles/op` on Linux (ecf5006, S56): user-mode cycles of the timed loop, counted on the benchmark's locked thread through `perf_event_open`. Run-to-run sd 10–33% lower than ns/op's on every benchmark measured (the host's clock frequency moves ns/op). `METRIC=cycles/op` in `verify/lrab.sh` and `verify/ab.sh`.
61. `BenchmarkCheckAndTouchHitCached` (ecf5006, X36): the cache-resident hit, its clock 64 ticks a touch so no register fills. `BenchmarkCheckAndTouchHitHot` has timed refused promotions since e9974b9; its loop and name stay, its comment says so.
62. `verify/lrab.sh` (81478eb, S55, S59, X37): six pads sized independently by a hash (three inside `filter.go`, before `touch`, `hit` and `locate`; the old three were one 1-D family), placement's and the runs' sd in the summary, `NULL=1` for an arm of the first arm's binaries run again. A null arm shows a spread of medians of 3 is mostly the host's: placement is 0–3.4% sd in cycles, not S54's 19%.
63. The `Filter`'s per-call fields in its header (349bff8, S60): `ct` shared a line with `waited` and `deferred`, so every Background or ConstantTime wait made other cores' next call miss (1.68x on lookups with one core adding); moved beside `seed`, 1.006, and single-goroutine speed 0.987–1.006.
