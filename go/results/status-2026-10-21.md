## Decisions

**Method**
- One change per commit, each with a test that fails before and passes after (performance changes: an interleaved A/B instead).
- Deterministic records are regenerated only for deliberate behaviour changes, and the commit says which. This session regenerated none: Background is off by default, and the two fixes don't touch any recorded scenario.
- Historical experiments keep the configuration they were recorded with.
- Race tests, repeated runs and a soak campaign are required before closing a concurrency claim. A new concurrency mechanism also needs a mutation check: undo each guard and show a test fails (A19).
- Speed is measured as A/B ratios on one host, arms interleaved; absolute times are reported with the host named.
- Tail claims on this host come with the host's own floor, measured in the same loop: `TestInsertTail`'s "spin 0.5us" class, or `TestHostFloor`.
- A micro-benchmark that moves when only the test files change is checked in a program that imports the library alone (S46: HitHot read 1.15x in the test binary, 0.95x in an importer).
- Experiments run env-gated in exported trees, never in the repo; adopted or rejected, the variant is kept as a patch in `verify/experiments/` with a README row.
- Validation that needs git history (`replay.sh`, `regression --full`) runs in a WSL clone. A worktree created from Windows has a `D:/` gitdir that WSL's git can't read.

**Taken this session**
- `Config.Background` is opt-in. It starts a goroutine, and its placements aren't deterministic, so the accuracy harness and the conformance vectors keep it off. Whether it becomes the default is the user's call.
- Background defers every move (no inline search). One move inline (E18) and per-set room locks (E19) were measured and declined.
- The placer never reads `Config.Clock`: it places a key at the key's last touch, and a loss counts from the history's newest event (c12f98b), so a lagging placement can't shorten the `Degraded` span.
- ConstantTime is unchanged by Background (no effect when both are set). Its waiting keys stay in the stash, and a key that only waited is no longer reported `Restored` (981cd70).
- Row 8: the two-phase warm is refuted (−9%); huge pages for batches (+5%) are not adopted.

## Remaining goals

1. **Row 8, first: adopt the prefetch batch.** `row8-batch-f298a7a.patch` with `TF_PF=3` reads 10.1–11.3 M keys/s (+15%, S47).
   - What it does: `PREFETCHT0` the chunk's primary lines, touch the keys found there, prefetch the rest's alternate lines, touch those last.
   - To port:
     - `prefetch_amd64.s` plus a plain-load fallback for other architectures;
     - the same scheme in `TouchAndCountBatch` and `VelocityCountBatch`;
     - an A/B on committed code (`verify/ab.sh`, `CheckAndTouchBatch` and the `TestThroughput` batched line);
     - a test that a batch with repeated keys answers as before (each key's own touch order is kept; order across keys changes).
2. **Row 11 on a quieter host.** Run `TestInsertTail` with `TF_BG=1` and `TestHostFloor` on bare metal or an isolated core. If the host's floor is low, the code's ~0.1% over 2 µs decides it. The rest of that share is the waiting path (~0.6 µs p50: room write and shared counters `deferred`, `waited`, the wait bits).
3. **Background as the default?** The user's call. It costs absent-key lookups 1.08–1.12x and starts a goroutine. Its placements make results timing-dependent, so tfbench and the vectors would pin it off.
4. **Row 7 (needs a decision).** The 0.05 target is out of reach for the 48-bit register (floor ~0.058; 0.05 needs ~1.25 s resolution near now, D18). Options for the user:
   - a wider register for keys whose short windows matter;
   - a target that weighs windows by use, or leaves out 1 s windows.
5. **Row 10.** Per-core cells for the hottest entries; 16 cores need another host.
6. **Row 9.** Probably host-bound (two DRAM misses at 189 ns); measure on a large-L3 host.
7. **Ideas not started.**
