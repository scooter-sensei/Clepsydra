# Improvement loop backlog

Checked on 2026-10-08: `verify/claims.md` maps each number here to a check (deterministic, replayed from git, or host speed), and marks the ones that turned out wrong. Patches for every reverted experiment are in `verify/experiments/` (diffs against 1e0ef14).

Scorecard: `bash bench.sh "label"` (race tests + cmd/tfbench, appends to results/history.md).

## Done
1. Partial-key cuckoo relocation (alt line from fp), iterative deepening to depth 2. Missed keys at 2.5x load: 5.0% → 0%.
2. Adaptive relocation budget (failure EWMA). Overfull-table insert: 12µs → ~0.4µs as first recorded; re-measured 3.7 µs → 0.30 µs (claims S5).
3. 28-bit slot identity (4-bit epoch, 12-bit tag). Static FPR 2e-7 → 4e-8 as first recorded (1 and 2 events in 5M/50M probes); at 1e9 probes it is 1.96e-7 → 1.40e-8 (claims X7).
4. CheckAndTouchBatch (overlapped misses). Cold hit ~100ns → ~45-55ns/key.

5. Any-size table (multiply-shift index, self-inverse alt), default 85% load: 42 → 19 B/key with 0 misses up to 94% load.
6. Relocation depth 3 / budget 500: misses at 98% load 0.19% → 0.066%. Correction (claims X6): measured against 3e9277c; the commit just before (9f2529f, depth 4 / budget 1000) missed 0.011%, so this change raised misses. Its insert-speed reason was not recorded.
7. Velocity register: 7 age-graded buckets (H/24 near now), closed-form advance, spill on overflow. Velocity MAE 0.129 → 0.087; heavy hitters no longer cap at 255.
8. Register fast paths: lazy victim scoring, in-place same-unit increment, reciprocal instead of divide.
9. VelocityCount estimates from the register's own epoch (no re-bucketing). MAE 0.087 → 0.081. Cache-resident 123 → 45 ns as first recorded; correction (claims X20): 88 → 71 ns re-measured.
10. CoarseClock option (cached clock, one refresher goroutine). String path 172 → 110 ns.
11. Concurrent first touches of one key no longer land in two slots (striped lock on the miss path only). Was ~12% duplicate slots and ~5% lost counts with 8 racing writers (replayed: 13.5% and 8.0% in one run; it varies). Correction (claims X15): the lock left a rare duplicate (10 of 400 runs under CPU load, 1 slot each), which item 16 closed. Steady insert +~15 ns.

12. Same-unit counter increment picks the first non-full bucket with one TrailingZeros instead of a loop. Hot-key hit 44 → 32 ns.
13. Displaced bit (taken from the timestamp, now 47 bits): an entry records which of its two lines it is in, and lookups match it. A key is compared only with entries homed at its own primary line. Static FPR 3.2e-8 → 1.8e-8 (1e9 probes), no speed cost. Storing which bucket choice was used is a known way to extend a fingerprint by a bit.
14. `Ticks` clamps negative durations to 0. A negative window used to wrap to a huge one and report every key as seen.
15. `TouchAndCountBatch` and `VelocityCountBatch` (same overlapped loads as CheckAndTouchBatch). Median of 6 runs, 1M-key table: TouchAndCount 154 → 106 ns/key, VelocityCount 129 → 83 ns/key. Empty batches no longer panic.
16. Installs publish the new key's register together with its word0, and touches only update a register that still carries their tag. A touch landing mid-install or mid-relocation used to reset a hot key's register: 12 of 20 runs of the relocation race test lost counts (up to 70), now 0 of 20 (replayed: 4–8 of 40 before, 0 of 200 after; the test itself was corrected, claims X14). It also closed the residual duplicate-slot race from item 11. Saturated inserts ~10% faster (one write fewer); correction (claims X21): no measurable change when re-measured. Correction (claims X17): two rarer causes of lost counts remained; items 18 and 19 closed them.
17. Scorecard: `hit DRAM` column (32M-key, ~600 MB table). This host's L3 is 260 MB, so the 1M-key "cold" table (20 MB) was really L3-resident. On DRAM: hit ~207 ns, batched ~95, absent-key ~115, VelocityCount ~190 (`go test -bench Huge`). Hits are latency-bound there because the CAS stops later lookups from overlapping; batches recover that overlap.
18. Abandoned moves keep their counts (0e073a5). A move whose source was touched mid-move withdrew its copy with whatever the copy had counted, and a touch still holding the copy could count into the dead slot. The copy is now retired word1 first and its extra events are added back. `TestAbandonedMoveKeepsCounts` (64 hot keys, 8 workers, 99% load): 2% of rounds lost counts before, none after.
19. Slot hand-over can't misdirect a count (75db206). A touch that had checked word0's fingerprint could CAS word1 after the slot went to a key with the same 12-bit tag. Installs now set word1 to a reserved busy tag first and touches re-read word0 after word1. Same test with shared tags: about 1 in 1,600 rounds lost a count before (34 of 200 runs), none in 60,000 after. Speed: see `verify/speed.md`.

20. Keyed integer hash (afdd877). `HashUint64` is a method keyed like `Hash`: a random seed, or SipHash-2-4 under `Config.Key`. The unkeyed SplitMix64 finalizer could be inverted to forge a victim's identity, evict it with 168 events, or put every first touch on one lock stripe (claims A1–A3). Cost: +3 ns per integer hash with the seed, +15 ns with SipHash (S26).
21. Eviction stash (afdd877): evicted live keys keep their history in a 4-way stash (1 entry per 64 slots, 0.44 B/key) and get it back on return. Missed keys at 1.15x: 58 → 0 (D1). Speed (S27): saturated inserts +42% (every insert evicts and stashes), hot VelocityCount +12%, other paths within ~10%. A flood that overruns table and stash still erases a history, but the key then reads `Degraded` (A3). The stress test caught a lost-count race in the first version (a stash copy withdrawn after another eviction had replaced it); victims are now stashed under their own claim stripe (A6).
22. Saturated bit and trust flags (afdd877). One timestamp bit (47 → 46 bits, ~2.2 years at 1 µs) marks a register that overflowed. `Touch`/`Count` return `Result` with `Upper` (edge bucket counted whole), `Saturated`, `Restored`, `Degraded`. Contract: not Saturated ⇒ Upper ≥ exact, 0 exceptions in 261,538 queries (A4, A5). A density heuristic tried first missed 689 of 187,219. Counts unchanged (D5, D7 identical).
23. Overflow sketch, per-key Degraded, ConstantTime. Histories the stash drops go to a count-min sketch over (key, Horizon/4 slice), 16-bit counters, one column per 8 slots (7.1 B/key): a flood no longer erases anything (Lost 0) and `Upper` never reads below the truth (A3, A7). `Count` adds a count-mean-min estimate only above 3σ of the noise, so keys that never spilled keep exact counts, and sets `Degraded` per key (0% of new keys during floods, was 100%). Strict limit of 20: 0.1% of new keys turned away after a 1x-slots flood (was 100%), 100% from 4x. Big floods still hide dropped histories from `Count` (A7). Tried first: restoring sketch counts into the table (the inflated keys then evicted real ones: a never-evicted offender read 992), plain count-min Degraded (99% of new keys flagged at 1x), noise σ from event totals (ignores that histories arrive in lumps; 18% false Degraded at 4x). `ConstantTime` (duration pad): seen-vs-unseen guess from one timing 85–89% → 51% at 3 µs (S28). Speed (S29): saturated inserts +65%, others within ~10%.
24. Security and cost round (results/security-cost-2026-10-09.md). The overflow sketch is now 8-bit × 4 rows × Horizon/2 slices, one column per 4 slots, allocated on the first spill: 4.7 B/key under attack and 0 otherwise, was 7.1 B/key always (A9, D6). Histories under 4 events are shed (`SpillMin`, `Shed()`): a 16x flood of one-event keys turns away 0% of new keys under a strict limit (was 100%), and evicted offenders after a 1x heavy flood read Count 18 of 20 (was 0) (A7, A10). Saturated inserts 31% faster (S32). Tried and documented: sleep, adaptive and yield pads for ConstantTime (all worse than spinning, S30), SipHash-1-3 (−35% keyed hash cost, not adopted, S31), 3 rows, wider or 16-bit shapes.

25. Overflow and ConstantTime round (results/overflow-ct-2026-10-09.md), at no extra memory or insert cost. The overflow count-min sketch is replaced by a ghost table in the same bytes (one 21-bit entry per dropped history, bucket floors keep `Upper` a bound): a 2x heavy flood turns away 1.8% of new keys under a strict limit of 20 (sketch 88–90%) and keeps 195 of 200 offenders' Count (sketch 0); reads take one line instead of four (A7, A11). Cost: 0.1–0.2% of new keys read `Degraded` through fingerprint matches while it is full. `ConstantTime`'s Count pads to its own tracked p99.5: 3.4 → 1.05 µs per call at the same leak, 2.1x the throughput under load (S33, S34). `AutoPad` tracks Touch's pad too. Alternate lines are loaded together before the cuckoo search (S35).
## Tried, no gain
- Sending displaced entries home (`homing.patch`): at insert (before using the alternate line) and on hits found in the alternate line. Under churn, keys in their second line drop from 37% to 30% (inserts only) or 33% → 24% (with re-touches), but no measurable hit gain on the L3-resident table, inserts +15 ns, and hits on full tables +18 ns from failed attempts. Reverted.
- Transparent huge pages (madvise) for tables ≥ 8 MB (`thp-madvise.patch`): granted (AnonHugePages matched the table), but no clear change on the 600 MB table either (hit 206–229 vs 196–246 ns). Reverted. Correction (claims X22): re-measured with alternating A/B runs, DRAM hits, absent lookups and batches were 11–18% faster; see Next.
- Reciprocal division for the built-in clock and `Ticks` (`reciprocal-clock.patch`): no change in the string path. The clock read itself (~38 ns in this VM, lfence/rdtscp-ordered) stops later work from overlapping, so the division was hidden.
- Raw RDTSC clock (`rdtsc-clock.patch`, benchmarks only): 19 ns vs 37 ns and doesn't block overlap (~20 ns saving on the string path), but needs TSC calibration and trust in invariant TSC across cores and VM migrations. Not done; CoarseClock already removes the clock cost.
- Issuing all eight relocation candidates' alternate-line loads before the cuckoo search (`reloc-prefetch.patch`): no measurable change in steady or saturated inserts (the 1M-key benchmark table is mostly L3-resident; misses are cheap).
- Per-line spill counts (skip the alternate line when nothing homed at the primary line is displaced; exact under a concurrent audit). Absent lookups ~10% faster, but steady inserts +15% and near-full inserts +15% from the extra counter traffic, and alternate-line hits wait on one more load. Reverted; the displaced bit it needed was kept (item 13). Patch: `results/experiments/spill-counts.diff` (against c8dbb54) and `spill-counts.patch` (ported).
- One CMPXCHG16B for both slot words instead of two 8-byte CASes (`cas2-cmpxchg16b.patch`): 19 vs 15 ns on this Xeon. Reverted.
- Branchless 4-way fingerprint compare in find (`branchless-find.patch`): hot hits ~10% faster, but cold lookups ~15% slower (the slot index becomes data-dependent, so the CPU can't run ahead on a predicted branch). Reverted.
- 2 MiB huge-page mmap for the table: THP was granted, latency unchanged (but see claims X22). (Same experiment as `thp-madvise.patch`; the explanation offered at the time was a guess.)
- 8-slot (128-byte) buckets (`eight-slot.patch`; also commits 983b804 / 9f2529f): 0 misses at 98% load and 3x cheaper near-full inserts, but ~10% slower everywhere else. Reverted. Re-tested on DRAM (round 8): near-full inserts 2945 → 464 ns and steady inserts slightly faster, but DRAM hits 208 → 227 ns, absent keys 127 → 200 ns (a bucket is two cache lines; the adjacent-line prefetcher doesn't make the second free — a hypothesis, not measured), saturated inserts 514 → 793 ns, and more false positives (measured 29 vs 18 in 1e9 probes, 1.6x; "~2x" was not measured). Still not worth it.
- Piecewise-linear density in the cut velocity bucket (`piecewise-linear.patch`): slightly worse than uniform (vel MAE 0.0834 vs 0.0809). Reverted.
- Alternate-line prefetch (plain load and asm PREFETCHT0), two-choice insert: hits got slower. Reverted. Correction (claims X23): re-measured, 40f9223 showed no measurable change. The plain-load version is commit 40f9223 (reverted in bc2e12d); the asm PREFETCHT0 and two-choice variants weren't kept (unverifiable).
- Lock-free duplicate repair (in-flight marker + lower index wins; `lockfree-dup-repair-bc2e12d.patch`, HEAD port `lockfree-dup-repair.patch`): cut duplicates 10x but can't be made symmetric (re-run: 16x at bc2e12d, 6x for the port; racy). Replaced by the stripe lock.
- Pure dyadic register (H/32, widths to 32 units; `dyadic-h32.patch`): same mean MAE as the H/24 geometry but 60s error 0.040 vs 0.024. Re-run on today's estimator: mean 0.0817 vs 0.0809, 60s 0.038 vs 0.024.
- Hot-key contention (round 8 check, not a change; `contention-bench.patch`): 4 goroutines on 1 key run at 10 ns/op aggregate, 16 keys at 16 ns, 16K keys at 22 ns. Same-tick touches skip the word0 CAS and full registers skip the word1 CAS, so a bot storm doesn't ping-pong the line. Touch elision isn't needed.

- Count-min overflow sketch (default from 55c82ed to 0651be5): replaced by the ghost table in the same bytes (e0a1e21), which keeps 2x floods to 1.8% strict collateral instead of 88–90% (claims A11). Kept in `overflow.go` for the experiments.
- Shadow work for ConstantTime (`ct-shadow-and-prefetch-toggle.patch`): narrows the seen/unseen gap without a pad, but Count's tracked pad gets the same leak cheaper, and for Touch the read-only insert walk costs more than the fixed pad (`results/overflow-ct-2026-10-09.md`).
- SpillMin 1 with the ghost table: dedup of one-event keys would survive floods, but inserts into a full table are 30% slower (S35). It stays a setting.
## Decided
- 2026-10-08: Priyasis chose to keep the 48-bit counter (exact heavy-hitter counts) over trading counter bits for identity bits. Options measured:
- More identity bits from the velocity register (measured, 1e9 probes):
  - 46-bit register + 14-bit tag (`register-46.patch`): FPR 1.8e-8 → 7e-9, vel MAE 0.081 → 0.085, per-key count cap per horizon 1000+ → ~876.
  - 44-bit register + 16-bit tag (`register-44.patch`): FPR → 0 seen (~1e-9 expected), vel MAE 0.088, cap ~630.
  - Correction (claims X3): the caps were burst counts at one phase. The current register's 60 s burst reads 770–1,273 depending on phase (46-bit: 638–889; 44-bit: 508–633), and steady traffic reads within 1% only up to 12 events/s (46-bit: 12% low at 10/s; 44-bit: 18–30% low). The ordering between the options holds.
- Truncated timestamps (needs a guaranteed sweeper when idle) would free up to 7 fingerprint bits without touching counts.

## Next
- Evictions at 97.8% load come from the bounded cuckoo search (claims D8). The stash now hides them (0 missed), but a deeper or BFS search would also cut stash traffic; measure the insert cost.
- Security (SECURITY.md, "What is left"): heavy floods of 3x slots and more overflow the ghost table's buckets, so their floors cover every key's `Upper` and offenders' `Count` is lost (A11); only `Overflow` moves the point. `ConstantTime` `Touch` still needs ~3 µs because of inserts that search; cutting that tail would allow a smaller pad.
- Per-key counts undercount above ~12 events/s (claims D7): the newest bucket holds 31 events per 2.5 s unit.
- THP for large tables: 11–18% faster DRAM operations in the A/B re-run (claims X22), against "no clear change" first time. Re-test on more hosts before adopting.
- Hot path: two CASes per touch (~12 of the ~27 ns hot hit, claims S25). Option: Resolution floor that skips the word0 CAS when the timestamp would not change.
- String path: faster hashing.
- Near-full (>94%) inserts cost µs; consider a per-line overflow hint so misses skip the alternate line.
